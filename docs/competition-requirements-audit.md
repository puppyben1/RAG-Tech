## 2. 赛题需求逐条提取

### 2.1 总体业务能力

系统应从多源异构资料中检索依据，回答监管条款、业务流程、指标口径、统计数据和场景合规判断问题，并给出可追溯证据；重点考察监管知识理解、复杂表格解析、跨文件检索、多跳推理、答案可验证性和幻觉抑制。  
来源：赛题主文档，表 1 第 9 行“命题概述”。

系统需要支持事实查询、流程核对、场景判断和证据追踪，并应处理资料分散、更新频繁、版本差异、旧规误用、条款定位不准和指标口径混淆。  
来源：赛题主文档，表 1 第 10 行“业务场景描述”。

### 2.2 技术任务

1. 对 Word/PDF 制度原文和 Excel 统计附件进行结构化处理。
2. 建立包含 `doc_id`、标题、发文机关、发布日期、文件类型、章节/条款/表格位置和来源 URL 的知识库。
3. 同时提供关键词检索、语义检索、元数据过滤和表格结构检索。
4. 支持按文件名、监管主题、业务领域、条款编号、指标名和期间维度召回。
5. 覆盖制度定义、适用范围、流程要求、金额阈值、保存期限、禁止性规定、统计取数和场景合规判断。
6. 交付可运行系统或服务接口、结构化知识库、检索与生成评测报告、数据处理和复现实验脚本。

来源：赛题主文档，表 1 第 12 行“攻关任务描述”。

### 2.3 量化验收指标

| 指标 | 赛题目标 |
| --- | ---: |
| 制度事实类问题准确率 | 不低于 85% |
| 表格取数类问题准确率 | 不低于 80% |
| 证据引用命中率 | 不低于 90% |
| 关键数字、日期、机构名称、文号错误率 | 不高于 5% |
| 库外或依据不足问题拒答/澄清率 | 不低于 80% |
| 入库规模 | 不少于 200 份制度/附件 |
| 文件解析 | Word、PDF、Excel 三类 |
| 证据粒度 | 条款级、段落级、表格单元级 |
| 单轮响应时间 | 满足比赛平台要求，原文未给具体阈值 |

交付件还应包括 RAG 系统或 API、知识库构建脚本、文档解析结果、训练/评测问答集、评测报告、运行说明和可复现环境配置。  
来源：赛题主文档，表 1 第 14 行“任务目标”。

### 2.4 数据与合规要求

每个下载文件的 manifest 应记录来源页面 URL、附件 URL、本地路径、文件大小、SHA-256、标题、栏目和 `doc_id`，用于溯源、去重和版本管理。评测集建议覆盖监管制度事实、条款/阈值、业务流程、统计表格取数、跨文件场景判断五类问题；标准答案建议包含 `answer`、`evidence`、`source_title`、`source_url`、`local_path`、`difficulty`、`qa_type`、`tags`。资料必须是公开官方资料或命题单位授权资料，并排除客户个人、账户、交易明细等敏感数据。  
来源：赛题主文档，表 1 第 15 行“数据集描述”。

注意：赛题第 15 行描述的“100 个混合文件 + 100 个 Excel + 20 份目录 + 42 条种子问答”与当前实际交付的 500 份文件和 300 条 QA 不一致。应以当前收到的文件为实际输入规模，但仍需满足字段和合规要求。

## 4. 硬缺口与风险

### P0：来源溯源未完成

`reports/metadata_quality_report.json` 显示 500/500 文档的 `source_url` 和 `attachment_url` 都为空；`reports/source_catalog_validation_report.json` 也显示两类 URL 候选均为 0。赛题明确要求来源 URL，当前答案最多能回到本地文件，无法回到官方来源页面和附件。这是“可信、可追溯”要求的直接缺口。

### P0：版本治理实际上未落地

`reports/version_audit_report.json` 显示 500 份文档全部为 `unknown`，`effective_date`、`expiry_date`、`version_group`、替代关系覆盖均为 0。虽然代码存在版本字段和过滤逻辑，但没有可用数据，无法可靠防止旧规误用。

### P0：当前环境不可复现

- 当前系统 Python 执行 `python -m jinrong.cli kb-status` 在导入阶段失败：`ModuleNotFoundError: No module named 'openpyxl'`；系统环境也缺少 `xlrd`。依赖虽写入 `pyproject.toml`，但当前解释器未安装。
- `frontend/node_modules` 不存在；`npm run build` 失败，提示 `vite` 未识别。
- 这意味着仓库内历史报告和截图存在，但当前工作机不能直接复跑后端或前端构建，尚未满足“可复现环境配置”的实际验收。

### P0：生成产物含旧机器绝对路径

manifest、多个报告和评测报告仍记录 `E:\work\code\JINRONG\...`，而当前仓库位于 `D:\Bisai\RAG-Tech`。例如 `data/processed/manifest.jsonl` 的 `local_path`、`reports/trusted_eval_summary.json` 的 `report_path`、`reports/retrieval_eval.json` 的 `report_path` 都指向旧机器路径。依赖这些字段的证据打开、文档详情和复现实验存在可移植性风险，必须重建或迁移为仓库相对路径。

### P1：核心元数据覆盖严重不足

历史质量报告显示：发文机关 93.2%，发布日期 1.0%，文号 2.2%，栏目 76.6%。API 虽支持日期、文号、栏目过滤，但低覆盖使过滤功能大部分情况下不可用，也会影响新旧规识别和最小充分证据定位。

### P1：所谓“语义检索”仍是哈希特征

`src/jinrong/vector_index.py:82` 的向量实现为本地 `hashed_embedding`，不是经过语义训练的 embedding 模型；重排也是规则版。它满足混合检索的工程接口，但不能等同于稳健语义召回。历史 60 条检索集又由当前检索链路筛选，存在明显自证偏差。

### P1：量化指标没有独立、统一验收

- 没有直接计算赛题要求的“关键数字/日期/机构名/文号错误率不高于 5%”。
- 没有记录单轮响应时间，也没有比赛平台具体阈值或压测结果。
- 证据命中、事实准确、拒答虽有代理指标，但评测集规模小、与实现共用规则，缺少独立 holdout 和人工复核。
- `QA数据.xlsx` 缺少赛题建议的 `source_url`、`local_path`、`tags` 独立字段。

### P1：没有独立测试文件

仓库中未发现 `tests/`、`test_*.py`、`*.spec.*` 或 `*.test.*` 文件。现有验证主要是 CLI 评测脚本和历史 JSON 报告，缺少单元测试、API 契约测试、错误输入测试和回归测试，修改后很难快速确认没有破坏既有能力。

### P2：解析与合规边界仍需证明

- `.doc` 使用二进制兜底或外部转换，稳定性低于 `.docx/.pdf`；需要对 32 个 `.doc` 样本做专项人工抽检。
- 页码只覆盖 3,409/7,132 文本单元，条款号只覆盖 1,828/7,132；尚不能对所有文本证据稳定返回条款/页码。
- 数据合规要求目前主要依赖资料来源假设，未见自动敏感信息扫描或数据合规审计报告。

## 5. 当前阶段判断

项目大致停在“功能完整的比赛型 MVP，已做大量定向评测，但交付与可信数据治理未收尾”的阶段。

已经完成的是：500 份资料入库、三类文件解析、结构化产物、检索/问答主链路、合规/拒答/多跳能力、API、前端和历史评测。尚未完成的是：官方来源补录、版本关系治理、元数据补全、路径迁移、当前环境安装与复跑、独立测试、独立 holdout 验收、性能指标和最终交付说明。

## 6. 建议恢复顺序

1. 安装并锁定 Python/Node 依赖，修复当前环境，先复跑最小后端健康检查和前端构建。
2. 将所有产物中的旧绝对路径迁移为仓库相对路径，并从当前 `D:` 目录重建 manifest、知识库和报告。
3. 按 `reports/source_gap_worklist_report.json` 的 500 条工作清单补齐官方页面 URL、附件 URL、发布日期、栏目和版本字段。
4. 建立独立 `tests/`，先覆盖解析、检索过滤、证据 schema、拒答、API 和路径可移植性。
5. 将评测拆成 dev/holdout，人工核验赛题五项量化指标，并补充关键实体错误率和响应时间报告。
6. 最后再替换真实语义 embedding/reranker、强化 `.doc` 解析和前端交付体验；这些不应优先于来源、版本和可复现性。

## 7. 审计边界

本次未修改业务代码，也未重跑会覆盖现有 `data/processed` 或 `reports` 的全量构建命令。由于当前依赖缺失，历史准确率只能标注为历史证据；在完成环境安装、路径迁移和独立复跑前，不应将其写成当前机器已验证结果。
