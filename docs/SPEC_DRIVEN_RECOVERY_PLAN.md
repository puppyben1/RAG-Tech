# 可信 RAG 项目 Spec 驱动恢复与交付计划

日期：2026-08-06  
范围：比赛交付恢复、需求收敛与验收设计；本文件不授权修改业务代码或覆盖现有生成产物。

## 1. 结论

本项目**适合轻量、增量、验收驱动的 Spec**，但**不适合当前阶段采用一次性、全量、先设计后实现的大一统 SDD（Spec-Driven Development）**。

推荐方式是：以赛题原文为最高需求基线，以当前源码为实现事实，以独立评测和可复现命令为验收证据；每次只为一个可交付增量写短 Spec，先明确契约和验收门槛，再实现、复跑、归档证据。旧的 `docs/SPEC.md` 应降级为“历史实现说明”，不能继续单独充当当前系统的验收规格。

## 2. 判断依据

### 2.1 为什么适合轻量 Spec

1. 赛题给出了可量化的外部约束。赛题主文档表 1 第 12 行规定了解析、混合检索、可溯源问答和交付物；第 14 行规定事实准确率、表格准确率、证据命中率、关键实体错误率、拒答率、入库规模、证据粒度和响应时间；第 15 行规定 manifest、评测集字段和数据合规要求。这些天然适合作为验收条款，而不是只写成路线图。
2. 系统已经有明确的契约面：结构化 JSONL、CLI、FastAPI API、React 前端和多类评测报告。现有实现包括 `/ask`、`/search`、`/documents`、`/kb/status`、`/eval` 及可信评测只读接口，见 `src/jinrong/api/routes.py:16-130`。轻量 Spec 可以围绕这些边界逐项冻结契约并补测试。
3. 当前问题主要是“实现事实与交付声明不一致”，不是从零探索架构。审计结论将项目定位为功能完整 MVP，但溯源、版本、可复现、独立测试和 holdout 尚未收口，见 `docs/competition-requirements-audit.md:89-132`。这类恢复工作需要短周期、证据驱动的变更规格。
4. 数据治理比算法替换更需要明确政策。500 份文档的来源 URL 为空、版本均为 `unknown`；若没有“什么文档可用于权威回答”的可执行规则，即使召回更强也可能更稳定地召回旧规或不可追溯资料，见 `docs/competition-requirements-audit.md:91-108`。

### 2.2 为什么不适合完整 SDD

1. 代码和数据管线已经成形。完整 SDD 会大量反向描述已有实现，收益低于先恢复可复现基线并补齐交付缺口。
2. 外部事实尚未稳定：比赛平台响应时间阈值未给出；来源 URL、附件 URL、发布日期和版本关系需要逐份核验。此时冻结完整系统设计会制造伪确定性。
3. 仓库已有多份长路线图和执行记录，但缺少单一可执行验收基线。继续新增“大而全”设计文档会加剧文档漂移；应改为一份索引、少量稳定契约和按变更归档的短 Spec。
4. 当前 `docs/SPEC.md` 已落后于源码。它只记录了较早的日期、文号、栏目等过滤（`docs/SPEC.md:276-301`），而代码还支持 `source_site`、`version_status`、生效日期、版本组、版本关系、指标、期间、现行版本优先和旧版纳入策略（`src/jinrong/api/schemas.py:14-39`）；源码还有可信评测 API（`src/jinrong/api/routes.py:123-130`）。该文档同时混入 `300/300` 历史结果（`docs/SPEC.md:12-22`）和旧机器绝对路径示例（`docs/SPEC.md:38-52`），说明它是实现快照，不是稳定的规范来源。

## 3. Spec 的边界

### 3.1 应纳入 Spec 的内容

- 赛题需求 ID、优先级、适用范围和明确的通过/失败条件。
- manifest、文档元数据、文本证据、表格证据、评测样本和报告的字段契约。
- `/ask`、`/search`、`/documents`、`/kb/status`、评测接口的请求、响应、错误语义和兼容策略。
- 权威来源、版本状态、旧版抑制、证据充分性、拒答和关键实体一致性政策。
- 构建顺序、环境前提、确定性要求、数据哈希、代码版本和产物追踪规则。
- 独立 holdout 的隔离规则、指标计算公式、阈值、样本复核和最终报告格式。

### 3.2 不应写进稳定 Spec 的内容

- 某次运行的 `300/300`、`60/60` 等结果；它们属于带时间戳、代码提交和数据哈希的验收报告。
- 当前采用 BM25、哈希 embedding 或某个具体模型的实现细节；除非它是明确的兼容约束，应放 ADR 或变更 Spec。
- 大段开发日志、完成进度、截图和临时路径。
- 尚未核实的来源、发布日期或版本关系；未知必须显式标记，不能由规则猜测后冒充权威数据。
- 前端视觉偏好和非比赛验收所需的产品化设想。

## 4. 建议的 Spec 文档结构

保留现有资料，但新增一个小型、可维护的规范区：

```text
docs/spec/
  README.md                 # 规范入口、权威顺序、当前批准版本
  REQUIREMENTS.md           # COMP-001... 赛题条款与范围
  DATA_CONTRACTS.md         # manifest、元数据、证据、评测 schema
  API_CONTRACTS.md          # API/CLI 契约及错误语义
  TRUST_POLICY.md           # 来源、版本、拒答、实体一致性政策
  ACCEPTANCE.md             # 指标定义、阈值、holdout 与复跑命令
  TRACEABILITY.md           # 需求 -> Spec -> 代码 -> 测试 -> 报告
  decisions/
    ADR-001-spec-strategy.md
  changes/
    CR-YYYYMMDD-short-name.md
```

每个 `CR-*` 只包含：问题与非目标、关联需求 ID、契约变化、迁移/兼容影响、验收案例、产物与回滚条件。只有稳定契约进入主 Spec；运行结果进入 `reports/acceptance/<run-id>/`，避免再次把状态混入规格。

权威顺序建议固定为：**赛题原文 > 已批准主 Spec > API/OpenAPI 与数据 schema > 源码实现 > 历史说明/路线图 > 历史报告**。发生冲突时必须建变更 Spec 或缺口单，不得静默以代码覆盖需求。

## 5. 依赖顺序

```text
P0-A 可复现基线
  -> P0-B 需求/契约基线
  -> P0-C 来源与版本治理
  -> P0-D 独立验收与交付闸门
  -> P1 检索、元数据与测试增强
  -> P2 解析、合规与产品化增强
```

来源与版本数据必须先于语义检索替换；契约基线必须先于批量改路径和重建产物；独立评测设计必须在针对评测优化前冻结。各阶段未过门槛时，不进入依赖它的下一阶段。

## 6. 分阶段执行计划

### P0-A：恢复可复现基线

工作项：

- 写 `CR-reproducible-baseline`，固定受支持 Python/Node 版本、依赖安装命令、入口命令、产物目录和禁止绝对路径规则。
- 锁定 Python 与 Node 依赖；从干净环境执行最小后端、前端构建和只读数据检查。
- 定义路径契约：持久化产物只保存仓库相对路径或可配置逻辑路径；运行时解析为当前工作区绝对路径。
- 先备份/标识现有历史报告，再从当前路径重建；禁止直接文本替换 JSONL 中的 `E:\work\code\JINRONG`。

验收门槛：

- 新环境按一份运行说明一次安装成功；`python -m compileall -q src`、后端 `/health`、最小 `/ask` 与 `/search` smoke、`npm run build` 全部通过。
- 从仓库根目录扫描生成数据和报告，不含旧机器路径；换一个工作区路径后仍能运行。
- 构建命令失败时返回非零状态并留下结构化错误报告；原始 `wendang/` 不被修改。
- 验收记录包含操作系统、解释器/Node 版本、依赖锁哈希、Git 提交和输入数据哈希。

### P0-B：建立单一需求与契约基线

工作项：

- 从赛题表 1 第 12、14、15 行生成 `COMP-*` 需求 ID，并建立追踪矩阵。
- 从实际 Pydantic schema、路由和数据产物反向校准 API/Data Spec；明确 `unknown`、`null`、404、无结果、拒答和降级行为。
- 将 `docs/SPEC.md` 标为历史快照或改为新规范入口；把运行状态和结果移出稳定 Spec。
- 为赛题未给出的“比赛平台响应时间”登记开放决策，未获得阈值前不虚构通过标准。

验收门槛：

- 每条赛题硬要求至少映射到一个契约和一个验收方法；无实现的条目标为 gap，不得写成已完成。
- OpenAPI、Pydantic schema、CLI 参数和 API Spec 字段一致；至少覆盖现有版本/期间/指标过滤和可信评测接口。
- 数据契约给出必填、可空、枚举、唯一性、引用完整性和兼容策略。
- Spec 审阅后带版本号和批准日期；所有后续业务变更均引用 `COMP-*` 与 `CR-*`。

### P0-C：来源、版本与权威证据治理

工作项：

- 以 `reports/source_gap_worklist_report.json` 为工作队列，人工/半自动核验官方来源页面、附件 URL、栏目、发布日期、文号和 SHA-256 对应关系。
- 定义版本枚举及政策：`current`、`superseded`、`unknown`、`not_applicable`；定义替代关系、有效期冲突和同组多现行版本的处理。
- 对 `unknown` 或无官方来源的监管文档默认不得生成“权威确定”答案，只能拒答/澄清或明确降级提示；统计快照按期间管理，可标 `not_applicable`，但仍需来源和附件追踪。
- 生成来源完整性和版本审计报告，所有人工判断保留证据与复核人。

验收门槛：

- 500/500 文件均能由 `doc_id + sha256` 追到官方公开来源或命题方授权记录；`source_url` 100% 有合法依据，附件型文件的 `attachment_url` 100% 有依据，不允许占位 URL。
- 所有文档均有经规则或人工确认的版本处置，`unknown` 为 0；不适用版本治理的统计快照必须有 `not_applicable` 与期间字段。
- 替代关系无悬空、自引用或环；每个版本组至多一个 `current`，冲突触发构建/验收失败。
- 随机抽检与高风险文档全检后，API 证据可返回来源、文件、位置、版本状态；旧版默认不进入权威回答。

### P0-D：独立验收与比赛交付闸门

工作项：

- 冻结 dev/holdout 隔离规则；holdout 不由当前检索链路自动筛选，且不参与规则、提示词和阈值调参。
- 覆盖赛题五类问题：制度事实、条款/阈值、流程、表格取数、跨文件场景判断；另设库外/证据不足负例。
- 固定指标定义：答案准确率、证据命中率、关键实体错误率、拒答/澄清率、检索 Recall@K/MRR、端到端延迟。
- 生成一键验收报告、失败样本明细、环境信息、数据/代码哈希和复跑说明。

验收门槛：

- 独立 holdout 上制度事实准确率 `>=85%`、表格取数准确率 `>=80%`、证据引用命中率 `>=90%`、关键数字/日期/机构/文号错误率 `<=5%`、库外或依据不足拒答/澄清率 `>=80%`。
- holdout 按类型给出样本量、置信区间或至少逐题明细，并由非实现者复核关键失败；不能用现有 `300/300`、`60/60` 或 `50/50` 代替。
- 平台延迟阈值确认后写入 Spec；确认前报告 P50/P95、冷启动和测试硬件，不宣称该项通过。
- 从空构建到 API、前端和评测报告可按运行说明完整复现，交付清单逐项校验通过。

### P1：增强质量，而非扩大功能面

工作项：

- 建立 `tests/`：数据契约、解析、路径迁移、API、过滤、版本政策、拒答、关键实体一致性和回归测试。
- 按字段适用性补齐发布日期、文号、栏目、条款页码等元数据，并记录“不可用/不适用”而不是伪造值。
- 在冻结 benchmark 上比较 BM25、真实 embedding、reranker；只有显著提升 holdout 且延迟/资源可接受时才替换。
- 加强错误分析：按文档格式、问题类型、版本状态和证据粒度分桶。

验收门槛：

- 核心契约和高风险政策均有自动回归测试，干净环境测试全通过。
- 元数据质量报告按“适用样本”计算覆盖率，目标与抽检规则写入变更 Spec 并达到批准阈值。
- 新检索方案相对冻结基线提升预设指标，且端到端可信指标不下降；报告包含成本、索引时间和 P95 延迟。
- 所有 P0 指标持续通过，无来源或版本治理回归。

### P2：边界能力与演示完善

工作项：

- 对 32 份 `.doc` 做正式转换或专项人工抽检；提高页码、条款号和复杂表格定位质量。
- 增加敏感信息扫描与数据合规审计报告。
- 在契约稳定后改善前端错误态、证据跳转、版本提示、移动端和演示脚本。
- 做容量、并发、缓存、可观察性和部署打包。

验收门槛：

- `.doc` 抽检集的解析完整性和证据定位达到变更 Spec 预设阈值，不再依赖不可解释的二进制兜底作为正式方案。
- 合规扫描有零未处置高风险项；所有发现均有处置记录。
- 桌面/移动核心流程 smoke 通过，无控制台错误，错误/拒答/旧版提示清晰。
- 部署包在目标环境完成一次从零演练，性能满足最终平台阈值。

## 7. 主要风险与控制

| 风险 | 影响 | 控制 |
| --- | --- | --- |
| 官方来源无法为全部文件反查 | P0-C 无法按赛题字段 100% 收口 | 区分官方公开与命题方授权记录；保留证据，不能猜 URL；阻塞文档不得用于权威回答 |
| 现有评测与实现同源 | 指标虚高、提交后失效 | 先冻结独立 holdout，再调参；保留逐题证据并由非实现者复核 |
| 全量重建覆盖历史证据 | 无法比较恢复前后差异 | 历史报告只读归档，新报告使用 run-id、提交和数据哈希 |
| 路径修复只改产物文本 | 隐藏代码中的可移植性缺陷 | 先定义路径契约，再从原始输入重建并换路径复跑 |
| 元数据规则把猜测当事实 | 版本误判、错误引用 | 每个关键字段保留来源证据、置信/确认状态和人工复核 |
| 真实语义模型引入成本与不确定性 | 延迟、依赖、结果回归 | 作为 P1 可替换实现，用冻结 benchmark 和回退方案准入 |
| 文档继续漂移 | Spec 与代码再次失配 | 主 Spec 只存稳定契约；每个变更必须带 CR、测试和追踪矩阵更新 |

## 8. 明确不应先做什么

- 不先替换 embedding、reranker 或接入更大的 LLM。当前瓶颈不是模型能力，而是来源、版本、复现和独立验收。
- 不先重做前端视觉或增加更多页面。现有页面足以支持契约验证，先保证数据与 API 可信。
- 不把 `300/300`、`60/60`、`50/50` 当提交验收结论；这些是历史、同源或小规模证据。
- 不直接批量替换生成产物中的旧绝对路径；必须从路径契约和构建逻辑解决，并从原始输入重建验证。
- 不为追求覆盖率自动编造来源 URL、发布日期、文号或版本关系。
- 不一次性重写所有历史文档或建立庞大的完整 SDD 文档树；先建立最小主 Spec 和第一个 P0 变更 Spec。
- 不在 holdout 冻结前继续针对现有题集调规则，否则无法再获得可信的泛化证据。

## 9. 第一周可执行切片

1. 第 1 天：批准本计划；创建 `docs/spec/README.md`、`REQUIREMENTS.md`、`ACCEPTANCE.md` 和 `TRACEABILITY.md` 的最小版本，登记开放决策。
2. 第 2 天：完成 `CR-reproducible-baseline`，锁依赖并在当前机器复跑最小后端/前端基线。
3. 第 3 天：冻结 API/Data 契约，建立最小契约测试；修复路径策略后在第二路径复跑。
4. 第 4-5 天：按来源工作清单先处理 holdout 和高风险监管文件，定稿版本政策；同时由独立标注者冻结 holdout。
5. 第 6-7 天：运行 P0-D 第一版验收，按失败桶生成下一批 `CR-*`，只修复阻塞比赛阈值的问题。

第一周结束的成功标准不是“新功能更多”，而是：任何成员都能从干净环境复现当前基线；赛题要求能追到契约、测试和报告；最关键文档有真实来源与版本处置；独立 holdout 给出可信的第一版差距。
